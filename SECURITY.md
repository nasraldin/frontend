# Security Policy

## Supported Versions

We actively maintain and provide security updates for the following versions:

| Version | Supported          |
| ------- | ------------------ |
| 1.x.x   | :white_check_mark: |
| < 1.0   | :x:                |

**Note:** Only the latest minor version within each major version receives security
updates. We recommend always using the latest stable release.

## Reporting a Vulnerability

We take security vulnerabilities seriously and appreciate your efforts to
responsibly disclose them. We are committed to working with security researchers to
address any issues found.

### How to Report

**For Critical and High Severity Vulnerabilities:**

- **Email:** security@ajrly.com

**For Medium and Low Severity Issues:**

- **GitHub Issues:** Create a security issue in our repository
- **Email:** security@ajrly.com (with appropriate subject line indicating severity)

### What to Include in Your Report

To help us understand and address the issue efficiently, please include:

1. **Description:** Clear description of the vulnerability
2. **Impact:** Potential impact and severity assessment
3. **Steps to Reproduce:** Detailed steps to reproduce the issue
4. **Proof of Concept:** If possible, include a proof of concept
5. **Affected Components:** Which parts of the codebase are affected
6. **Suggested Fix:** If you have suggestions for remediation
7. **Timeline:** Your preferred disclosure timeline

### Our Response Process

We follow a structured approach to address security vulnerabilities:

| Timeline      | Action                                                |
| ------------- | ----------------------------------------------------- |
| **24 hours**  | Initial acknowledgment and triage                     |
| **72 hours**  | Detailed assessment and severity classification       |
| **7-14 days** | Status update and remediation plan                    |
| **30 days**   | Target for fix release (may vary based on complexity) |
| **90 days**   | Public disclosure (if no fix available)               |

### Disclosure Policy

We follow responsible disclosure practices:

- **Coordinated Disclosure:** We work with reporters to coordinate public disclosure
- **Credit Attribution:** We credit security researchers with their consent
- **CVE Assignment:** We will request CVE IDs for qualifying vulnerabilities
- **Public Disclosure:** Issues are disclosed once fixes are available and deployed

### Security Update Process

1. **Assessment:** Evaluate the vulnerability's impact and severity
2. **Fix Development:** Develop and test the security fix
3. **Testing:** Thorough testing across supported environments
4. **Release:** Deploy the fix through our release process
5. **Communication:** Notify users and stakeholders
6. **Documentation:** Update security advisories and changelog

## Security Best Practices

### For Contributors

- Follow secure coding practices
- Use dependency scanning tools
- Report suspicious activity immediately
- Keep dependencies updated
- Use strong authentication methods

### For Users

- Keep your installation updated
- Monitor security advisories
- Use HTTPS in production
- Implement proper access controls
- Regular security audits

## Security Tools and Processes

We use several tools and processes to maintain security:

- **Dependency Scanning:** Regular automated vulnerability scanning
- **Code Analysis:** Static and dynamic code analysis
- **Security Testing:** Automated and manual security testing
- **Access Control:** Role-based access control for repositories
- **Audit Logging:** Comprehensive audit trails
